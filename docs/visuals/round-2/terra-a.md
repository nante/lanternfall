## D4 — Darkness, clock and server boundaries

Use four bands **0–3** and Chebyshev distance (`packages/game/src/model.ts:8`). For a source of radius `R`, its level at distance `d ≤ R` is `max(1, 3 − floor(3d/(R+1)))`; it is 0 outside. Use a 3-tile free carried test lantern, 4-tile street lamp, and 3-tile brazier/altar. Sources contribute only on their floor and the strongest band wins; equal-strength colors use a stable source-ID tie-break. All carried sources contribute to the same shared field. Visual flicker changes color inside the granted band, never the rule radius. Outdoor day ambient is 3, dusk/dawn step through 3, 2, 1 and 0, and outdoor night is 0; roofed interiors and the undercroft have ambient 0. Because any positive level reveals, outdoor visibility changes at the 1↔0 boundary, not gradually through all bands. Show that boundary honestly and assess whether the pop feels acceptable.

Street lamps and braziers stay on by day and night. I adopt Terra B's choice over my round-1 lamp schedule: it is simpler and preserves the existing lamp description (`engine.ts:546`). Windows brighten decoratively at dusk but are not rule sources. No free cave torch, actor self-glow, eyes-only proxy, torch fuel, shield cost, regeneration penalty or AI change in v1. The first lantern starts on for the test and can be freely toggled. Darkness is frightening because an unchanged creature may approach without advance warning; it is not made stronger or faster. Walking, healing and untargeted area spells remain available. Later, separately test a five-minute fuel unit and a beetle noticing a lit carrier one tile farther away, with an explicit low-fuel indicator. These are proposals, not implemented or balanced behavior.

Put clock, source definitions, lantern state/command, tile light and visibility in `packages/game`, enabled for the local prototype and default-off for production. A viewer sees a dynamic entity only when on the same floor, within the view limit, with unobstructed line, and either its tile has positive light **or** it is within one Chebyshev tile. Adjacency is tactile awareness, not a light source and not sight through a wall. Define a supercover line: an opaque endpoint can receive light and be seen, but blocks beyond; where the ray crosses an exact corner, either opaque side blocks. Closed doors block; open doors pass. This is new: `Geography.sight` checks the static opaque set and ignores door state (`packages/game/src/world.ts:61`, `packages/game/src/model.ts:13`). Do not silently change existing monster sight/AI.

Enforce the predicate in the Engine, not a dark shader: filter hidden monsters, other players, corpses and ground items in `view()`, reject forged hidden target IDs and targeted spells, recheck visibility immediately before chase and attack, and clear lost targets and automatic routes without canceling a manual path (`engine.ts:557`). Blind area spells may still hit, but a hidden victim's effect position and identity are withheld; the caster still sees their own burst and damage to self. In addition, audit `look`, adjacent access, NPC interaction, notices, battle list, minimap and effect origins. Filter/redact effect data according to visibility **when the event occurs as well as when delivered**: effects persist 1.6 seconds (`engine.ts:439`), so an old hidden hit must not suddenly reveal itself when its tile lights up. The current `view()` sends nearby full monsters, players, effects, doors and accessible items (`engine.ts:636`); `Mob` includes `home`, `target` and `damage` (`model.ts:43`), and `PublicHero` includes `target` (`model.ts:33`). Audit nested IDs and positions too, not just the top-level entity lists. Self-damage feedback remains even when its origin is redacted.

`GameView` needs a bounded tile intensity/color field and a viewer visibility mask. Do not send light or source positions outside that viewer's observable region just to draw the picture; a visible pool may intentionally hint that a light is nearby. Static map geometry and NPC spawn data are already client-distributed, so this is not a promise of secrecy from a modified client. The client must still mask unpermitted static NPC sprites, labels, glows and interaction affordances, and brightness settings must never expand the server's entity visibility. A gameplay rollout requires the complete audit, not only a prettier local screenshot.

Use a **40-minute active-world cycle** derived from `state.time`: day 18, dusk 4, night 14, dawn 4 minutes. This adopts Terra B's cycle in place of my 48-minute proposal; it is a starting value to test, not a balance finding. The server pauses simulation when nobody is connected or combat-locked (`apps/server/src/index.ts:62`), so time intentionally pauses. Colors can transition between authoritative bands, but visible entities must follow the actual mask. Use straw/moss by day, copper/violet at dusk and blue-black/amber at night; read the time from ground, roofs, lamp pools and restrained water glints even when there is no sky. The lookout adds moon and stars. For phase comparison, reset the isolated local fixture to a selected initial `state.time`; don't run a separate client clock or scrub the live Engine backward through cooldowns and corpse timers.

## Risks and verification

**Performance is unverified.** On a named MacBook-class integrated GPU, compare baseline and candidate on the same 60-second town/cave/bridge route at 1080p and 1440p; record browser, DPR, output and internal sizes, zoom, actors, sources and warmup. Aim for frame-time p95 ≤16.7 ms and 1% low ≥45 fps; record all render passes and CPU time. Use supported asynchronous GPU timing or a browser trace, not `gl.finish()` as the sole timing method. Start with a 1024 directional shadow, no point shadows and a one-texel-per-tile field; remove decorative grass, mist and shadow resolution before reducing actor readability. A low target resolution does not eliminate geometry, shadow, fill or full-output upscale cost.

The room allows 16 clients and sends views every 100 ms (`apps/server/src/index.ts:38`, `:62`). Measure total tick **including** all views and actual serialized bytes at 16 representative players, with moving sources and doors. For scale only, a 45×45 field costs 2,025 bytes if packed into one byte per tile, plus about 254 bytes for a bit mask, before metadata and encoding; JSON or other encoding can be larger. Current near-entity distance is less than 22 tiles (`engine.ts:638`); wide viewports and the chosen zoom must not display beyond the field or grant more vision. Compute shared floor light once when appropriate, then each viewer's line/mask; invalidate on movement, doors, source and phase changes, and on transaction rollback (`apps/server/src/index.ts:33`). Do not ignore gameplay sources to hit a budget.

**Readability and accessibility:** a player must identify self, adjacent threat, wall edges, ladder and selected tile in the dark. Offer brightness/contrast for permitted pixels, distinguish hazards by shape and value as well as color, and provide reduced flash and motion. Test a dim display, bright room, open and closed door, and multiplayer light transitions. The starting dark-night rule is a hypothesis; shorten or lighten night if it is frustrating, without weakening the server mask.

**Art, information and saves:** measure how long Opus takes to make and revise the first slice; 22 frames and one backdrop are not evidence of affordable production coverage. Information filtering and event-time redaction need real adversarial checks before any multiplayer claim. The server parses saved state and can reset after a failed parse (`apps/server/src/index.ts:20`); add defaults or a tested migration before any production activation. Prototype estimates, sprite depth, final visual quality and performance remain unverified.
