# Lanternfall Studio — round 2 cross-check (Terra)

I read the brief and all three round-1 plans, checked their claims against the current code and content, and ran a small in-memory Engine probe. This is a planning review, not an implementation or a visual verification. References below are relative to the project root. The project is currently not a Git repository (`git status` reports no repository); I did not initialize one or modify the database.

## Where the plans agree

All three recommend a separate, loopback-only Vite/TypeScript studio, explicit saves, validated content that the game actually consumes, stable gameplay IDs, and a real-engine simulator rather than a second combat implementation. They agree that icons, terrain textures and box-built actors are different kinds of assets; PNG export from an external pixel editor is useful, but a PNG cannot simply replace an animated box rig. They also agree on keeping the finished lighting/post look, avoiding a full Aseprite clone and deferring model editing.

The code supports that direction. `model.ts:35–86` and `engine.ts:1–24` currently supply live values directly; none of the three JSON exports is imported by the game. `icons.ts:2–35` uses SVG rect runs, `textures.ts:39–106` builds a procedural ground atlas, and `actors.ts:23–85` builds box rigs. `package.json:9–16` has Vite, `tsx` and tests but no studio script. An editor that only changes JSON is therefore not yet useful in the game.

## Disagreements and recommendations

### 1. Scope and order: all three plans front-load too much

My plan and Sol's M0 make all three exports authoritative, including all 12 rigs, before the app exists. Opus moves a long list of additional constants and formulas before shipping the editor. This is the largest shared over-scope for a one-developer tool: `model.ts` mixes protocol identities and values, while `engine.ts` uses them throughout inventories, combat, quests and persistence. Rig migration additionally changes animation and rendering. None of that is needed to prove the first end-to-end sprite and balance workflow.

**Recommendation:** ship a small vertical slice across both requested areas: editable item/creature/spell balance fields that actually affect the game, plus icon editing and one hand-painted ground PNG import. Wire only those data sections first, keep other JSON sections explicitly read-only/non-authoritative, and document which source owns each field; never expose a control whose saved value the game ignores. Add broader progression, quests, texture families, and rig migration as separately verifiable slices. A minimal staged balance migration should still include both server and client consumers for the fields it moves. The first useful release needs a working Studio and changed game behavior, not every exported file and every preview feature.

Sol rightly says ground art has more leverage for the handmade world than inventory icons alone (`terrain.ts:199–225` shows ground plus separate grass blades). I would move a **single** ground import into that first slice instead of deferring all environmental art to my M4 or Sol's M3. Keep the icon editor very small. My draft's comprehensive viewport, simulator, cross-process content hash and all-rig migration should not be prerequisites.

### 2. What balance to externalize

Opus wants almost every embedded number, including corpse lifetime and vault slots, migrated into editable progression; Sol adds a smaller set of shield/regen/potion/starter constants; I proposed leaving unexported constants in code. **My narrower approach is better initially.** Corpse lifetime, item stack limits and slot limits have protocol/state consequences (`model.ts:62,88,115`; `engine.ts:48,304–325`); making them configurable expands compatibility and validation work without being necessary to tune creatures or gear. Shield, regen and potion constants matter for balance, but their existing Engine behavior can be reflected in later simulations while they remain labeled fixed assumptions. Add a field when there is a concrete tuning need, not to eliminate numeric literals.

All plans are right that the existing exported numbers need deliberate wiring before the Studio edits them: e.g. `engine.ts:267–275,307,369–407` embeds spell power, respawn and attack formulas; `view.ts:7,341` independently embeds movement speed; quest requirements and reward wording are partly literals (`engine.ts:174–181`, `main.ts:392`). Item prices also appear verbatim in NPC dialogue (`model.ts:133,141–142`). Show or update dependent text when the related value becomes editable.

Opus proposes splitting spell `spread` immediately; Sol and I preserve the existing field with explicit kind-specific semantics. Prefer the latter during the first migration: healing calls `random(base / 4)` and Ember calls `random(12)` (`engine.ts:265–275`); `balance.json` encodes those as `0.25` and `12`. Splitting is a reasonable later format change, but a discriminated validator and clear labels avoid a migration now. Verify floor/inclusive random behavior and loot-object versus tuple conversion.

Opus moves every numeric formula to `rules.ts` and proposes a grep banning literals in Engine. Sol and I prefer per-Engine injected balance/rules plus extraction only where actually shared. That's better: keep the simulation using `Engine.tick` and keep independent analytic equations to a minimum. A regex is a weak guard for behavior and pushes unrelated constants into configuration. Preserve RNG-call order when moving any formula.

### 3. PNGs, palette and procedural fallback

Opus proposes baking every generated texture to PNG, deleting the generators, and seeding a shared palette by clustering all existing colors. Sol and I keep procedural fallback and use PNG overrides. **Keep the fallback.** It lets the owner replace one material at a time, avoids a large one-time art migration, and supports a defensible before/after comparison. `textures.ts:41–98,110–159` contains different ground, wall, roof and prop generators; there is no existing image pipeline to remove safely. Clustering colors changes pixels and is an art decision, not a parity-preserving migration; a mandatory shared palette, its linter, sheet editing, fill/line/mirror tools and broad model templates are not necessary in v1. A simple optional palette per icon is enough.

Sol's opaque-terrain rule and exact-size/explicit-alpha icon import are useful: do not silently quantize, rescale, or drop alpha. A small fixed slot map with missing slots falling back to generators is simpler than requiring a full manifest entry for every procedural material. If an explicitly selected PNG is missing or invalid, show an error rather than silently claiming the override is active. Content-hashed images written before the manifest are a good way to avoid a manifest referring to an incomplete image, but are needed only when the PNG feature ships.

Keep the existing dimensions and sampling (`textures.ts:28–34,39–40,101–106,109–112,134–155`; `terrain.ts:24–36,89–105`): 48×48 ground across 2×2 world tiles, 16×32 wall, 16×16 roof/prop, nearest filters and wall world-projection. Water is special: `terrain.ts:101–105` replaces the sampled atlas color with procedural waves, so Opus's blanket bake/import plan would not make a painted water tile appear. Leave its control unavailable until the shader is deliberately changed. Prop planks are distinct from the ground plank tile.

For packaging, Sol's `apps/client/public/...` plus a base-relative URL is a plausible simple route: the client Vite config uses `base: './'`, and Electron loads `dist/client/index.html` from disk (`apps/client/vite.config.ts`, `apps/desktop/main.cjs:3–5`). Verify the built Electron asset path and provide the Studio, which has a different Vite root/port, its own explicit route to preview those files. Opus's example `import.meta.glob('/content/art/**/*.png')` does **not** by itself point at repo-root `content/art` under the current client root; allowing the filesystem is not the same as changing what the leading `/` resolves to. My proposed repo-content glob has the same build/root issue to resolve; it was not proven.

### 4. Preview and rig parity

Opus says overriding art and calling `WorldView.setFloor(0, {})` rebuilds the floor. It does not: `view.ts:175–178` uses `this.floors[z] ??= buildFloor(...)`, so the old floor is reused. `update()` similarly only creates a rig when an actor ID is absent (`view.ts:261–269`). Opus's claim that a diorama needs zero refactoring is therefore too optimistic. Sol correctly calls for explicit art injection, invalidation/rebuilding and disposal; my plan called for extracting the shared camera/lights/post shader immediately.

**Recommendation:** try reusing a small `WorldView` fixture with an explicit draft-art seam and correct floor/actor invalidation. Do not first extract a whole renderer framework; extract only the seams that prove necessary. For the initial ground import a repeat swatch plus save/reload into the real game may suffice, with an embedded game-look diorama following once useful. `view.ts:87–138,175–198,331–356` shows that the actual view owns an animation loop, unstored ResizeObserver, cached floors, lighting and limb animation; repeated preview rebuilds need a real lifecycle/dispose path, including care with shared geometry/materials (`actors.ts:3–7`). A raw swatch is not evidence of the final lit appearance.

Sol identified a real export discrepancy that my report left as only an unverified hypothesis: `actors.ts:72–74` calculates the first grub segment's Y as `0.285 * 0.42 = 0.1197`, while `content/models.json` stores `0.12`. Thus the brief's claim of identical model values is not bit-exact. Verify acceptable geometry, limb ordering and animation before replacing the current rigs; no need to migrate or edit models in the first slice. Sword and guard pole parts do appear under `armR` in the exported JSON, but check all transforms and ordered limbs before relying on it (`actors.ts:28–49`, `view.ts:351–355`).

### 5. Reload, persistence and recovery

Opus claims Vite reload reconnects using the saved token automatically. It does not: `net.ts:14–32` saves the token and reports disconnect; `main.ts:89–124` shows a gate with a manual Continue button. All three recommend a restart rather than in-place engine mutation, which is sensible. Prefer a documented **save → restart server if balance changed → reload client → Continue** path first; add watchers or bounded reconnect only if they improve actual use. If automating, test the watcher signal and cached-module invalidation. Watch balance on the server, not all art: Opus's `content/**` would cause unnecessary game-server restarts for icon/PNG changes.

Sol proposes clamping restored hero/monster HP and mana; Opus clamps monster HP; my plan preserves state. **Preserve existing saved state without a new clamp** in the migration. `index.ts:18–24` restores the saved world and clears connection/target state; `Engine` seeds only if the monster table is empty (`engine.ts:19–22`). A clamp is a persistent gameplay change, not a neutral reload. Warn that old monster HP can exceed a lowered maximum until later behavior changes it, and starter gear applies only to new characters. `LANTERNFALL_DB` already permits a separate disposable database (`index.ts:13–16`) for fresh-state checks. Do not delete `.local/lanternfall.sqlite`, as Opus's leave-out section suggests, or run `git init` on the owner's project as a prerequisite. Simple local backups are worth considering precisely because the project has no Git history, but should be explicit, bounded, and made **before** replacement; copying the previous file after rename, as Opus's sequence states, would copy the new bytes unless the previous bytes were retained.

My and Sol's content hash in `/health` and welcome detects mixed snapshots, but is additional protocol/build coordination. For v1, the explicit ordered restart/refresh and visible failure is simpler. If automatic concurrent reload is later introduced, add a shared revision/mismatch indication and test it rather than claiming independent watcher events are synchronized. The server currently only handles `SIGTERM` (`index.ts:64`); verify actual watch shutdown and persistence before promising zero lost ticks.

### 6. Balance results and simulator

All plans choose the real `Engine`, which is correct: it is independent of the server and Three.js (`engine.ts:1–5`), and `TownRoom` ticks at 100 ms (`index.ts:38`). Sol's advice to pass an immutable rules snapshot per Engine, use fixed nonzero seeds, start adjacent, report victories/deaths/timeouts separately, and compare drafts using the same seeds is worth adopting. One floor is enough for an isolated surface arena (`world.ts:6`); my and Sol's two-floor fixture is unnecessary unless testing floor travel.

Opus's analytical downtime and respawn cap are useful exploratory hypotheses, but not reliable first-release hourly predictions: actual regen requires food, hero attacks start on the first tick, deaths restore HP and drop the pack, and spawns are blocked if a present player is **less than** six tiles from home (`engine.ts:318–325,332–341,369–390`). Continuous hunting also has travel, looting, inventory, healing and failures. Offer modest expected sellable loot values and a clearly labeled successful-fight throughput estimate only when assumptions are explicit; do not label it measured or sustained income. A break-even price is not profitable arbitrage: use `sell > buy` with a real seller and buyer, not Opus's `>=` (`engine.ts:282–295`). Loot rolls are independent, so a sum above 3 is not inherently invalid (`engine.ts:312–314`).

I ran an exploratory in-memory 7×7 single-mob fixture, 200 nonzero seeds per mob, level 1 with the real starter cudgel/armor/food, adjacent start, 100 ms ticks, no consumable use, stopping on death or kill. Rat: 200 wins, mean winning time 5.13 s, gross incoming damage 6.40; beetle: 200 wins, 27.16 s, 67.73; grub: 43 wins/157 deaths, winning time 37.04 s, winning damage 142.67; boar: 191 wins/9 deaths, winning time 31.28 s, winning damage 104.80. These are sampled, scenario- and seed-dependent outcomes, not population guarantees. They broadly support Opus's concern about grub danger but show why its ~44 s/~201 damage grub estimate must not be presented as the observed average of completed live fights. Food runs during fighting, and regeneration cannot automatically be converted into post-fight downtime without defining the policy. The code uses modulo reduction and quantized chance rolls (`engine.ts:24–25`), so even exact uniform formulas are idealizations.

Do not use Opus's proposed blanket ±15% analytic-versus-simulation test as a correctness gate: rough DPS, first-attack phase, randomness, deaths and conditional victory means are different quantities. Nor assume 500 trials take tens of milliseconds without measurement. Prefer a small seeded parity regression for a real Engine fight, spell spread and loot conversion, plus explicit timeout/death cases and isolation of two different balance snapshots. Keep the worker and optional CLI until the simulator is actually built.

My proposed observer is safer than assuming the effect stream captures all healing. Sol's effect-ID cursor is useful for avoiding double counting, but `tick()` silently applies fed regen (`engine.ts:339–341`) and level-up HP changes (`engine.ts:136–145`); they are not `heal` effects. Effects contain positions, not actor IDs (`model.ts:123`), and persist for 1.6 s (`engine.ts:335`). `block` is emitted only on a zero-damage attack with a nonzero block roll (`engine.ts:400–408`); it is not a count of every partially blocked attack. For simple adjacent solo fights, cursor-based incoming hit totals are feasible; if reporting total regen/heal or attribution in more general scenarios, instrument the actual state changes or use carefully verified reconstruction without changing RNG/order. Likewise, `p.hp` after death cannot detect death because `kill()` restores it immediately.

### 7. File safety and validation

All three support explicit writes, Zod validation, revision conflicts and same-directory temp-file rename. Favor Sol's fixed allowlist, bounded request, same-origin checks and unique temp files; serialize Studio saves and reject stale revisions. A local hash check does not provide cross-process atomic compare-and-swap: another editor can race between check and rename. Per-file rename is not a multi-file transaction. Preserve a dirty draft on conflict and validate cross-references before publishing a changed document. No authentication service, arbitrary filesystem endpoint, external commands, or separate database is needed.

Opus's illustrative icon validation accepts the character `0`: `Number('0') - 1 < palette.length` is true, even though palette indices are one-based and `.` means transparency. Use an explicit allowed alphabet and check its index is nonnegative and within the palette. The current 27 icons have palette symbols `1`–`4` and `.` (`content/icons.json`); future imported colors must not be silently discarded. Stable ID tuples and preserving the order of `grounds` and `things` are important because those arrays become numeric map values (`model.ts:8–14`), and water is hard-coded as index 7 (`terrain.ts:97–105`). Avoid introducing import cycles between IDs, schemas and default content.

## Additional factual corrections and gaps

- Opus's explanation of malformed `#724fS` is wrong. `hex()` slices it as `72`, `4f`, `S`, so the blue parse is `NaN`, which becomes `0` in `ImageData`'s clamped array; it is not `parseInt('fS', 16) = 15` (`textures.ts:5,17,81–85`). I checked the slicing in Node. Fixing it changes appearance and should be a separate, intentional art decision, not a claimed identical bake.
- Opus says the texture bootstrap can delete generators and still immediately look identical while also fixing that color and clustering the palette. Those operations conflict with an exact visual parity claim; water and separate grass/prop geometry further limit what a bake replaces.
- Opus's sample schema imports IDs from `model.ts` and has `model.ts` re-export definitions from the content module. Without extracting IDs or otherwise separating modules, this creates a circular dependency. Sol's `ids.ts` or my dependency-free ID module is the safer arrangement.
- Sol's requirement that every gold drop fit `stackMax` is relevant, but additional validation also needs to consider starter pack/container capacity and the corpse's 12 slots (`engine.ts:48,57,122–130,304–314`). Avoid expanding those limits casually. Cross-file reference checks should be performed against the proposed content and the other current documents; avoid presenting a partial save as a multi-file transaction.
- Opus's formula example estimates food cost as 60 gold/hour at a 3-gold loaf lasting 180 s. That arithmetic is correct only for continuous feeding with unlimited access and no waste; `engine.ts:125,250,339–341` starts characters fed, permits feeding above the fullness threshold on the last use, and only regenerates when fed. Label it an assumption, not measured expenditure.
- My earlier recommendation to expose all quests/starter/merchant data alongside the first editor needs narrowing: the hard-coded quest item and copy, and existing player inventories, make some fields larger migrations than simple number edits. Make them read-only until each is wired and its saved-world behavior is understood. My proposed full-reload/revision system also needs the same scope reduction described above.

## Ranked decisions for the final plan

1. **Define the first useful release.** Ship a vertical slice for real item/creature/spell tuning, a small icon editor and one ground PNG override, with an end-to-end save and game reload. Stage broader progression, quest, model and full preview work after that. Explicitly mark untouched export sections non-authoritative and non-editable.
2. **Choose the authority and parity boundary.** Stable IDs stay typed in code; each migrated value has exactly one runtime source. Validate the selected JSON at load/save, wire both client and Engine, and preserve current ordering, rounding and RNG behavior. Keep spread semantics explicit and convert loot shape deliberately.
3. **Choose the handmade-art path.** Import exact-size PNGs, preserve nearest sampling and procedural fallback, and initially support a fixed ground slot. Do not bake/delete all generators, force palette clustering, or promise painted water/character sprites. Add wall/roof slots once the path works.
4. **Choose how edits reach a running game.** Explicit save and ordered server restart/client reload/Continue is sufficient first; keep persisted world state, explain existing HP and starter-kit effects, and use a separate disposable DB for fresh-world checks. Automate watchers/reconnect and add content revisions only after verifying the manual loop.
5. **Choose balance evidence.** Start with directly inspectable values and small, honestly labeled economy estimates. Then run the actual Engine with a draft rules snapshot, fixed seeds and explicit policies; show victory/death/timeout and avoid claiming a solo fight measures hourly town income.
6. **Choose preview fidelity and ownership.** Start with a repeat/raw asset view and actual game reload; when embedded preview is valuable, reuse `WorldView` through minimal explicit invalidation and disposal. Verify the final look in the real game. Defer generic rig migration/editor until its rounded export and animations have been checked.
7. **Choose local write protection.** Use fixed file/asset slots, validation, bounded same-origin requests, explicit saves, revision conflicts and unique atomic replacement. Preserve drafts; consider bounded pre-write local backups. Do not modify SQLite or initialize Git automatically.
