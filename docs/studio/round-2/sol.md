# Lanternfall Studio — round 2 cross-check (Sol)

The three plans agree on the architecture. Terra's incremental PNG overrides are the better art path; Opus's balance-first milestone is the better way to get a useful editor shipped. My round-1 plan needs to lose several prerequisites, especially model migration, new tuning groups, automatic reconnection and runtime content-version gating. Combine the common core into a smaller tool, then add the real-engine simulator and world-texture workflow as separate increments.

This review checks `BRIEF.md` and all three round-1 reports against the current repository on 2026-11-09. Code and content were read-only; only this report was written. References below are repository-relative file paths with current line numbers. The numerical probes ran in memory through the existing modules, without starting the game server or opening SQLite. No browser/rendered visual parity or implementation test pass is claimed.

## 1. What all three get right

| Agreement | Repository evidence and implication |
| --- | --- |
| The game must consume the files the editor writes. | `engine.ts:1–4`, `model.ts:37–86,128–145`, `icons.ts:2–35` and `actors.ts:12–85` still own executable definitions; none consumes the exports. Editing JSON alone has no gameplay effect. |
| Keep gameplay IDs typed and fixed in the first editor. | `model.ts:8–14,35,88–119` makes IDs part of tile indices, saved items, monsters and commands. `town.ts:95–136,185,228–234` and `actors.ts:59–85` contain specific look/creature references. An arbitrary-ID editor would require more than data entry. |
| Give each Engine its own validated balance snapshot. | The present constructor takes only map/state (`engine.ts:19–22`) and imports global definitions. Instance-local content lets baseline and unsaved draft fights coexist without changing defaults or the running server. Whether that input is called `Balance` or `Rules` is secondary. |
| Use the real engine for fights. | `Engine`/`Geography` have no server, database or renderer imports. Actual combat includes inclusive integer rolls, first-tick attacks, skill growth, fed regeneration and immediate revival (`engine.ts:24,318–341,369–408`); copied DPS arithmetic cannot reproduce that. |
| Keep existing actor rigs and lighting. | Actors are colored boxes on pivot groups (`actors.ts:23–85`), animated/scaled by `view.ts:261–290,341–356`. PNG textures are useful; directional character sheets are a different renderer project. |
| A local Vite tool is sufficient. | Root `package.json` already has TypeScript, Vite, Three.js and Zod, with `apps/*` workspaces; the client is plain TypeScript. A new framework, Electron shell, service, database or account system adds no first-version value. |

I independently rechecked the exports: all items, merchants and creatures match the TS definitions after normalizing loot tuples to objects; existing spell core fields and shell-quest data match. Rasterizing the current icon SVGs yields the same pixels as all 27 JSON icons. These are useful migration baselines, not proof that an injected-content implementation already works.

## 2. Opus: disagreements and factual corrections

### 2.1 Bake everything and delete generators: reject as the first art migration

Opus §2.4/M3 proposes baking every texture and deleting its generator. Terra and I retain generators behind explicit imported overrides. **Prefer Terra's incremental approach.** One imported grass, wall or roof can ship without producing and auditing the entire existing texture library. `groundAtlas`, `wallTexture`, `roofTexture` and `plankTexture` are already narrow seams (`textures.ts:101–159`); keeping a fallback does not require a general procedural editor.

Opus also misses a functional exception: water's sampled atlas color is overwritten by animated GLSL (`terrain.ts:99–105`). A water PNG will not control its appearance. Leave that slot disabled/procedural. Grass blades, foliage, rock colors and much prop geometry remain procedural outside `textures.ts` (`terrain.ts:216–272,305–373`), so baking that file is not a conversion of the whole world to authored pixel art.

The proposed project palette, color clustering, texture painter, icon sheet round-trip, line tool, fill and mirror controls are optional art-tool features, not prerequisites for PNG import. A shared palette can be an advisory swatch list after actual use. Automatically clustering current colors would also invalidate the claimed identical-after-bake baseline.

### 2.2 Reload: narrow the server watcher and keep Continue

Opus §1.4 says the client reconnects with its stored token and needs no changes. **False.** `net.ts:14–32` joins only on request and reports unexpected leave; `main.ts:93–124` shows the gate and joins on Continue (except the explicit `?as=` path). Stored credentials enable recovery, not automatic recovery.

Its `tsx watch --include 'content/**'` also contradicts §2.4's promise of no server involvement for PNG changes: an explicit all-content include watches art too. **Prefer Terra/Sol's balance-only watch.** Art saves should reload the game client without disconnecting players. Prove JSON/new-PNG invalidation in the installed Vite configuration; neither automatic HMR nor a custom reload plugin should be assumed necessary before that check. Cached floors/actors/icons make a full game reload a sensible v1 contract (`view.ts:175–178,263–278`; `main.ts:343`).

Use the existing Continue button initially. Correctly persisting a watch restart matters more than hiding a single click. The server handles only SIGTERM today (`index.ts:64`); the actual watch signal and shutdown path remain an implementation acceptance check, not an established fact.

### 2.3 Schema sketch: fix real errors, avoid a dependency cycle

- `content.ts` imports ID values from `model.ts`, while the proposed compatibility exports in `model.ts` read `balance` from `content.ts`. That creates a value-initialization cycle. **Prefer the separate IDs/schema/default-loader boundary described by Terra and Sol.** It prevents both the cycle and loading art/default JSON when only a validator is needed.
- The icon predicate accepts `0`: `Number('0') - 1 < palette.length` is true. It needs a valid-symbol check and a lower bound. Palette limits are a choice: today's maximum is four colors, not nine. Supporting only `1–9` initially is valid if explicit; expanding to the documented 35-symbol alphabet is also small. The suggested `[0-9a-z]` alphabet contains 36 symbols, not 35, and needs an explicit mapping to preserve today's one-based encoding.
- A generic spell record with optional `range` permits an attack spell with no range and allows changing the behavior kind of fixed IDs. **Prefer the constrained heal/attack shapes in Terra/Sol.** Preserve the current distinction between fractional heal spread and absolute Ember spread (`engine.ts:265–274`; `balance.json:318–355`). Renaming to explicit spread fields is reasonable, but is not required before the first consumer: kind-specific validation plus field labels is smaller and preserves the existing export.
- “Adding a creature is a two-line code change” understates the work. Persisted `Monster.kind`, map spawns and creature rendering also encode the known kinds (`model.ts:24,98`; `town.ts:228–234`; `actors.ts:59–85`). Keep creation/renaming outside the studio.

### 2.4 Do not externalize every numeric literal

Opus correctly identifies missing regen/block/potion tuning, but then exposes corpse lifetimes, container sizes, stack limits, assist XP, shrine policy and movement constants before the editor exists. **Prefer Terra's wire-the-existing-export-first scope.** My own extra tuning groups should also wait. A first balance editor remains useful with documented fixed assumptions.

In particular, stack size is used in saved-item and command validation (`model.ts:62,88,115`), container slots interact with the command's slot limit (`model.ts:115`; `engine.ts:48`), and changing container size affects persisted inventories. These are not all equivalent to changing a creature's attack. Extracting every equation and policing numeric literals by grep would create a refactor project. Share progression/definitions and any roll-limit helpers actually needed by reports; leave combat sequencing in Engine.

### 2.5 Economy: adopt the concern, reject the certainty and arbitrary lint

Opus is right that slow fed regeneration and food upkeep matter: level-1 regen is 1 HP/3 seconds (`engine.ts:339–341`), and a 3-gold loaf supplies 180 seconds (`model.ts:52`). Paying for continuous loaf-fed time is ideally 60 gold/hour. That is an assumption, not the observed cost of a hunt: starter food, drops, healing, shrine trips and failures change it.

I checked Opus's difficulty premise with 500 real-engine fights per creature, seeds `91827..92326`: a fresh 7×7 grass arena, one adjacent monster, current starter equipment/HP/mana/food, no casts/potions, 100 ms ticks, stop at monster death, hero `deaths` increment, or 300 seconds. New effects were consumed by ID and notices drained. UUIDs were not compared. Results:

| Creature | Victories / deaths / timeouts | Mean victory duration | Mean gross incoming damage on victories |
| --- | --- | --- | --- |
| Rat | 500 / 0 / 0 | 5.18 s | 6.03 HP |
| Beetle | 500 / 0 / 0 | 28.10 s | 69.92 HP |
| Grub | 71 / 429 / 0 | 36.88 s | 139.72 HP |
| Boar | 473 / 27 / 0 | 32.82 s | 111.41 HP |

This supports “grubs are dangerous for this profile,” but Opus's 44-second/201-damage grub estimate is not a mean completed fight in this engine. Victory-only figures have survivor selection; they cannot imply safe hourly farming. These are fixture results, not measured town gameplay or proof of performance on every seed.

**Prefer Terra/Sol's explicit successful-fight throughput plus chosen overhead**, with failure rates visible. Opus's spawn-count cap is at best an upper bound: respawn depends on a present player being at least six tiles from home and an unoccupied home (`engine.ts:389–390`). Paths, spawn distribution and recovery do not become modeled by taking a minimum of two rates. Do not add `designLevel`, “one hour to unlock” warnings, loot-chance-sum thresholds or editable resell thresholds in v1. Loot rolls are independent (`engine.ts:314`), so their probabilities are not a weighted distribution.

Arbitrage requires **sell > buy**, not Opus's `>=`; equal prices give no profit. It also requires actual buyer and seller routes (`engine.ts:282–294`). Item prices are global, not merchant-specific, so `bestSellPrice` need only check whether a buyer exists. Terra's 3.2 ideal gold/rat example is correct: 2 coins plus `0.6 × 2` for tails; no merchant buys the loaf (`model.ts:65,128–143`). Affordability should subtract current gold and be labeled a budget ratio, not an expected stopping time.

### 2.6 Preview and simulator claims need narrower contracts

Reusing `WorldView` is a good idea, but Opus's `setFloor(0,{})` does **not** rebuild a floor: it returns the cached `floors[z]` via `??=` (`view.ts:175–178`). Draft texture updates need explicit cache invalidation/replacement. Existing actors likewise retain their rigs. `WorldView` already starts its own animation loop (`view.ts:138`), so feeding the same `update()` every frame is unnecessary and repeatedly rebuilds route geometry (`view.ts:299–301`). Update when fixture/draft state changes.

Effects persist for 1.6 seconds (`engine.ts:335`), have positions rather than actor IDs (`model.ts:123`), and passive regen emits no effect (`engine.ts:341`). Thus `p.hp` plus “read e.effects” is not yet a damage/healing collector. Prefer deduplicated effects in a stationary solo fixture, state accounting for regeneration, and `p.deaths` for terminal detection. Add an observer only if those cannot supply the promised metric.

The proposed analytic-TTK-within-15% test cannot establish simulator parity; attack phase, death conditioning and stochastic kill thresholds can violate the tolerance without a bug. Use deterministic behavior comparisons with identical content/scenario/seeds. “Tens of milliseconds” is unmeasured; do not turn it into a performance promise. A single-floor combat arena is valid: Geography checks available floors (`world.ts:6`); two floors are useful for visual presets, not a duel prerequisite. Leashing is a distance rule (`engine.ts:394`), not a consequence of walls being absent.

### 2.7 File writes and existing-world handling

Opus is correct that this directory is not currently a Git repository (`git status` fails). **Do not run `git init` or delete SQLite as part of studio implementation.** Neither is required by the request. Existing `LANTERNFALL_DB` support (`index.ts:14`) already allows disposable-world checks without touching the owner's world.

Adopt hash conflicts and atomic replacement, but use a serialized write queue and unique sibling temp files, as Terra specifies; a shared `<file>.tmp` and unchecked concurrent saves are insufficient. The proposed backup step occurs after replacement: to preserve the old version it must retain the old bytes or make the backup before replacement. One recovery copy may be worthwhile without Git; a rotating 30-version subsystem can wait. Fixed slot-to-path maps, bounded requests and same-origin/Host checks are small boundary protections for a local writer. Reading only PNG IHDR dimensions does not establish that the file is a decodable image; verify actual decoding before declaring an import valid.

## 3. Terra: agreements, disagreements and useful additions

Terra agrees with my snapshot injection, fixed IDs, explicit reload, indexed icons, independent loot rolls, generated fallback, restricted character representation and save-file preservation. Its warnings about existing monster state and positional effects are supported by the code. It also distinguishes cash from replacement-use value correctly.

There are four changes I recommend:

1. **Reuse WorldView before extracting a second preview shell.** Terra §2 calls for extracting camera/light/post helpers; my plan starts with an injected-content `WorldView` adapter. Prefer the adapter: `view.ts:87–138,175–201,378–433` couples camera, targets, lights, resizing and post, and `terrain.ts:199–374` already accepts a map. A small synthetic surface/cave scene exercises the actual pipeline. Extract only what the adapter proves necessary. Add lifecycle cleanup when scene replacement is introduced: there is currently no dispose method and the ResizeObserver is not retained (`view.ts:136–138`). Opus's diorama-first instinct is worth adopting, with its cache assumptions corrected.
2. **Do not migrate models as a prerequisite.** Terra M1, like my M1, makes all three exports authoritative before an editor can ship. Yet model editing is its final milestone. That front-loads 12-rig parity/animation work unrelated to editing a price or icon. Wire balance for the balance editor and icons for the art editor; leave model JSON explicitly read-only until its builder/editor ships. Do not offer save controls for files the game still ignores.
3. **An observer and runtime content handshake are optional.** Actor-ID observation is useful for moving/multi-actor scenarios, but a stationary solo melee fixture is measurable without extending the engine event API. Likewise, `/health` and `welcome` currently carry no content hash (`index.ts:42,60`); Terra's version gate/retry mechanism adds protocol/client/server work. Start with written-to-disk status and documented restart/Continue, not claims of confirmed application. Add a read-only hash diagnostic only if reload verification proves difficult; automatic gameplay gating can wait.
4. **Keep “small local editor” independently useful.** Terra M2 emphasizes icon painting while balance tables wait until M3 and PNG world art until M4. Opus's tables-first sequence is faster for the balance request; Terra's own top recommendations favor early handmade assets. Use a clear small first slice (balance forms plus one icon workflow), then separate world-texture import and simulation increments. Neither should wait for model controls, advanced icon tools or automatic reconnection.

Adopt Terra's explicit saved-state explanation: `Engine` seeds only an empty monster table (`engine.ts:21`), and restoration clears targets/connections rather than replacing HP/items (`index.ts:22–24`). Also adopt its distinction between validation errors and balance warnings, shared content validation with no Node dependencies, PNG preload before atlas creation, exact nearest/sRGB/wrap behavior, and packaging checks for Electron's disk-loaded build (`apps/desktop/main.cjs:5`).

## 4. Revisit my own plan

- **Too much before first value.** Remove model migration, all supported texture families, added regen/block/potion groups, dev reconnect, content-hash application confirmation and broad client/server changes from the first-editor gate. Keep them as targeted later work. Shared validation and a functioning JSON consumer are necessary; full content platform completion is not.
- **Simplify my manifest.** My required generated/png entries for every ground, wall, roof and prop are heavier than Terra's sparse override map. Prefer absent = intentionally generated; present = required PNG (show a load error if missing). Exclude water/void and prop planks initially. One allowlisted filename per editable slot can ship first; immutable hashed images plus manifest-last becomes useful when replacement consistency warrants it, not a prerequisite for the first icon/balance editor.
- **Do not make boot-time clamps implicit.** I recommended clamping restored hero HP/mana and monster HP downward. Opus clamps monsters; Terra preserves their current HP. These are different behavior policies, not established reload behavior. Prefer preserving the existing world in v1 and explaining that new monster HP applies fully on fresh spawn. Increased max HP will not heal existing entities; equipped items and capacities also retain state consequences. Do not normalize or repair saved inventories automatically. Test changes against fresh fixtures/disposable DBs.
- **Keep geometry findings proportional.** My grub warning was correct but should be precise. I compared all rig part colors, bone assignments, sizes and relative positions after flattening identity groups, plus pivots/kind/height: 11 rigs match within floating-point tolerance; all five grub segment Y positions differ by 0.0003 world units (`actors.ts:73`; `models.json:2518–2605`). For example, live Y is `0.1197`, export is `0.12`; the first width is already `0.285`. This needs an explicit tolerance or corrected export when model migration happens, not a prolonged visual overhaul. Sword/guard-pole armR placement matches.
- **Correct the plank diagnosis for everyone.** The malformed literal is at `textures.ts:82`, not Opus's line 46. The parser at line 5 slices `'#724fS'` into `'72'`, `'4f'`, `'S'`, producing `[114,79,NaN]`; typed pixel storage turns the last channel into 0. It does not parse `'fS'` as 15. Preserve this current output in migration baselines; fix the color in a separate deliberate art edit.
- **Preserve studio drafts in the actual import graph.** My report says content events must not erase drafts, but a fetch-based store alone does not ensure that. Importing Engine/default loaders or game `icon()` can transitively import the same saved JSON and trigger studio HMR. All three plans need to check this graph. Prefer pure draft renderers/schema modules and narrowly suppress/handle content notifications in the studio, retaining dirty drafts on conflicts. Do not rebuild a second asset store or silently reset drafts to disk.
- **Keep verification meaningful after retuning.** Existing tests hard-code starter cash, costs, quest counts and spell mana (`tests/engine.test.ts:25–94`). Passing them unchanged establishes the initial migration, not permanent compatibility with intentional balance edits. Keep engine behavior fixtures with explicit content when injection exists; avoid a golden assertion against forever-changing authoring defaults. No per-field UI test suite or source-literal lint is needed.

## 5. Ranked decisions the final plan must settle

1. **What constitutes the first useful version?** A standalone `npm run studio` with explicit saves/revert/validation, existing-item/creature/spell/progression forms and a minimal icon edit/import path, each backed by a working game consumer. No model migration, full texture conversion, automation or simulator prerequisite. Subsequent increments add authored world textures and seeded fight comparisons; both belong in the overall plan.
2. **What is the authoritative content boundary?** Existing balance/icon JSON, fixed TS IDs, pure schemas and an immutable per-Engine balance input; no schema↔model initialization cycle or mutable global draft. Wire every field exposed as editable. Keep formulas in executable code and behavior-specific spell typing/spread semantics.
3. **What does Save/apply mean?** Save validates and writes one document. Balance changes restart the dev server; art changes reload only the game client. Initially recover via Continue. Preserve drafts, report failures, verify actual watch/shutdown behavior, and require a rebuild for built/Electron content. Do not claim application acknowledgement without implementing it.
4. **How does handmade art enter the game?** Tiny indexed-icon tooling plus flattened PNG imports for opaque 48×48 ground, 16×32 wall and 16×16 roof overrides. Keep generators as fallback; no water import, shared-palette conversion, full painter or actor sprite-sheet rewrite. Use one asset location and prove both Vite and disk-loaded builds resolve it.
5. **What happens to the owner's saved world?** Preserve it. No deletion, reset, automatic HP clamp, ID removal or inventory repair. Explain existing-versus-fresh spawn behavior and use the existing DB environment override for disposable checks.
6. **What do balance numbers promise?** First show prices, stat/progression changes and buyer-aware expected cash. Add bounded real-Engine melee batches with the same nonzero seeds for baseline/draft, gross damage, victory/death/timeout counts and victory-conditioned TTK. Hourly/affordability numbers must display overhead, food/consumable assumptions and exclusions. No asserted town-economy prediction or analytic ±15% correctness gate.
7. **How is file writing kept small and reliable?** Loopback Vite middleware, fixed document/asset slots, bounded validated requests, same-origin checks, serialized revision checks, unique temp + rename, draft-preserving conflicts. A simple recovery copy is sensible without Git; rotating backups, automatic Git setup and multi-file transactions are unnecessary.
8. **How much renderer refactoring is justified?** A small `WorldView` adapter with explicit draft sources, cache replacement and cleanup when preview lands. Keep actual camera/light/post/mapping/scales. Extract helpers only where needed; rendered verification remains an implementation task, not something this planning review established.
9. **Which tuning/editor features wait?** Model builder/part inspector, new balance groups, generator controls, palette enforcement, advanced pixel tools, spell/consumable policies, CLI conveniences and content-version gating. Keep each behind a demonstrated use case rather than expanding the first deliverable.
