# Lanternfall Studio — round 1 research and plan

## Recommendation

Build a local Vite app in `apps/studio` that edits the existing JSON and a small, explicit set of PNGs. First make the game consume the exported data with behavior-preserving validation; then add an icon pixel editor and PNG texture import, balance tables, and a simulator driven by the real `Engine`. Preserve the current renderer and rigs. This is a tool for authoring content, not a new renderer or game server.

### Current integration points and hazards

- `packages/game/src/model.ts` owns the fixed item/slot/monster/spell IDs, definitions, progression functions and NPC definitions. `packages/game/src/engine.ts` imports them as module globals; it also embeds combat, regen, spell power, starter kit and death values. `town.ts` supplies fixed monster and NPC references, and `world.ts` supplies the geography used by combat.
- `content/balance.json`, `icons.json`, and `models.json` are exports, not runtime inputs. Read-only comparison confirmed item definitions, merchants, quest reward fields, all four creature definitions (after converting loot), and each spell's existing core fields match the TypeScript; rasterizing the current SVG runs also matched all 27 JSON icons. This did not verify model geometry or full combat parity. The JSON creature loot is `{item, chance}[]`, while `Engine.dead` currently expects `[ItemKind, number][]`. Spell `spread` is `0.25` of the computed base for healing, but an absolute `12` for Ember. Blindly using one interpretation changes combat.
- `apps/client/src/icons.ts` generates SVG from rectangle runs. `apps/client/src/render/actors.ts` builds real box rigs, not flat sprite sheets; `view.ts` animates the ordered legs and arms and scales the rigs. `textures.ts` generates the terrain; `terrain.ts` constructs and caches shader/material/texture resources. `main.ts` also duplicates some displayed balance, including the hard-coded five-shell quest text; `view.ts` duplicates `STEP_MS = 300`.
- The server uses `tsx watch` and persists state in `.local/lanternfall.sqlite`. On restart `apps/server/src/index.ts` restores existing monster HP and inventory and clears targets/connections; it does **not** reseed a populated monster table. The client `net.ts` currently reports a disconnect; it does not automatically reconnect. A data reload is not a fresh world.
- Ground textures are 48×48 for 2×2 world tiles, wall textures 16×32, and roofs 16×16. `terrain.ts`'s ground shader replaces water's atlas sample with animated procedural colors, so a water PNG alone would not appear. `textures.ts` currently contains malformed plank color `#724fS`; verify its visible output during parity checks instead of silently normalizing it as part of a data move.

## 1. Move definitions into validated shared content

### Contract and types

Keep the existing JSON structures initially; do not re-export from TypeScript at runtime or maintain two editable copies. Add browser-safe `packages/game/src/content-schema.ts` for Zod schemas and inferred types, and separate runtime wiring from pure schema/rules:

- Keep stable ID tuples in TypeScript, e.g. existing `itemKinds`, `equipSlots`, `npcRoles`, plus explicit `mobKinds` and `spellIds`; derive `ItemKind`, `MobKind`, `SpellId` and Zod enums from those tuples. They are protocol, save-file and map identities, not balance values. The first studio edits values for existing IDs; adding/removing IDs requires a deliberate code/save compatibility change.
- `BalanceSchema` mirrors the existing keys `progression`, `items`, `creatures`, `spells`, `merchants`, `quests`, `starter`, using `z.record(z.enum(...), ...)` for exhaustive known ID records and strict objects. Infer `Balance` from the schema; do not assert that arbitrary JSON is a typed record. `Creature.loot` becomes `[{ item: ItemKind, chance: number }]` all the way through `Engine.dead`.
- Keep the existing spell shape but validate it as a discriminated union: heal `{ kind:'heal', base, perLevel, perMagic, spread }` means `base + random(base * spread)` with the existing integer flooring in `Engine.random`; attack `{ kind:'attack', range, base, perLevel, perMagic, spread }` means `base + random(spread)`. A more explicit `spreadFraction`/`spreadMax` rename is reasonable later with a one-time migration, not silently now. Both versions retain `words`, `name`, `mana`, `level`, `cooldown`.
- `IconsSchema`: a record of icon IDs to `{ palette: ['#rrggbb', ...], pixels: string[16] }`; exactly 16 characters per row, `.` is transparent, `1` indexes palette[0], and so on. The current files use only `1`–`4`. For a small editor support a documented `123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ` alphabet (at most 35 colors); reject any symbol without a palette entry. Validate every item `icon` and the three spell IDs plus `bag`, `person`, and `menu` used by `main.ts` against the icon record.
- `ModelsSchema`: record keyed by existing look/creature ID; each value has `{kind, height, bones: Record<string,[number,number,number]>, parts:[{bone, color, size:[number,number,number], pos:[number,number,number]}]}`. `body` is the implicit bone; all other part bones must be present. Sizes and height must be positive finite numbers; colors must be valid hex. Require the existing human `legL`, `legR`, `armL`, `armR` and creature `leg0...` order needed by `view.ts` (allow no legs for `mireGrub`); validate keys/kinds required by `town.ts`, `view.ts`, and `mobKinds`. Validate bone names and limb ordering explicitly, not through accidental JSON object order.
- Validate finite nonnegative costs, weight and damage, positive HP and time intervals, integral counts/XP, chance in `[0,1]`, ordered inclusive integer gold ranges, positive skill divisors/bases, and growth rates that guarantee progression. Validate that the XP curve is strictly increasing for supported levels and that progression loops terminate; explicitly cap the supported range/XP and match the game’s `level`, `skillFrom`, and `magicFrom` behavior at the limits. Check starter slots/pack and item references, quest item/reward, merchant stock, model IDs and icon cross-references. Reject invalid writes with field paths and useful messages. The schema for each file is independently usable; cross-file validation runs on the assembled content before save/startup.

At the boundary parse raw imported JSON with schemas. Enable `resolveJsonModule` in `tsconfig.json` and use JSON imports compatible with the installed Node/tsx and Vite toolchains; verify the actual import syntax in both `npm test` and the Vite build. A dedicated default-content module may import the static files once; schemas and rules must not import Node APIs or the default content. Production client builds must bundle the same files (including Electron's `file://` build), not read the repository at runtime.

### Engine and client wiring

Prefer explicit immutable inputs, so a simulator can use an unsaved draft without replacing a global singleton. For example:

```ts
// packages/game/src/content-schema.ts
export type Balance = z.infer<typeof BalanceSchema>;
// packages/game/src/engine.ts
new Engine(map, state, balance); // validated Balance snapshot for the lifetime of this Engine
```

Implement `getDef(balance, kind)`, `xpAt(balance, level)`, `level`, `maxHP`, `maxMana`, `capacity`, `skillFrom`, and `magicFrom` with an explicit balance argument or a small `createRules(balance)` object shared by engine and UI. Migrate all callers in `engine.ts`, `main.ts`, `view.ts`, and tests together. `Engine` should own its `balance`; do not leave some formulas reading default module globals. Keep identifiers/protocol schemas in `model.ts` or a dependency-free IDs module to avoid a circular import. Derive public types from schemas and keep compile-time exhaustive IDs for `town.ts`, commands and persisted state.

Make the exported values actually authoritative: replace `STEP`, player/monster attack intervals, regen interval, respawn delay, death fractions, melee factors, progression coefficients, starter equipment/pack, quest `item`/`need`/`reward`/`gold`, and spell powers in `Engine`; replace `view.ts`'s step interval and `main.ts`'s hard-coded quest count/item text. Preserve constants not exported, such as potion randomness, shield block formula, fed-dependent regen increments and corpse lifetimes, until they are deliberately exposed in a later narrow change. The UI must show only fields wired to actual behavior. Keep existing inclusive RNG, floors/ceilings, event ordering, and quest behavior. NPC dialogue contains literal prices and fixed reward descriptions; parameterize the relevant lines or flag them as manual copy so editing prices/rewards cannot silently make dialogue lie.

`icons.ts` should render the JSON grid to the same crisp 16×16 SVG contract, with safe color and label escaping. In `actors.ts`, replace `looks`, `human`, and `creature` construction internals with a generic builder from `models.json`: create `root` and `body`, named bone groups at the stored pivots, box parts under the named bone, and the same ordered `legs` and `arms` arrays expected by `WorldView.frame`; retain `Rig.kind`, `height`, casting/receiving shadows, mesh sharing, scales, and `corpseMesh` separately. Test every exported rig against the existing silhouettes and walk/attack animations; explicitly check sword placement attached to armR and the no-leg grub. JSON is claimed to match the source, but treat this as a parity hypothesis until verified, including SVG overlaps and draw ordering.

### Reload and saved state

Use deliberately simple **save-and-reload**, not a promise of seamless live mutation:

1. In development, `npm run dev:server` uses `tsx watch --include content/balance.json apps/server/src/index.ts` (confirm the include path/glob from the root). On a validated atomic save, `tsx` restarts the server with a fresh parsed snapshot; it keeps using SQLite. Verify `SIGTERM` persistence in the actual watcher, and report a restart failure clearly. This disconnects players. A manually malformed external edit may make startup validation fail; show the path/error and wait for correction rather than silently starting with incorrect data. Studio-originated invalid data never reaches disk.
2. The game Vite config explicitly watches imported content outside the client root and triggers a full page reload on balance/icons/models/asset changes. A full reload rebuilds HUD icons, floor atlases/materials and existing rigs instead of assuming Vite HMR updates objects already cached by `WorldView`. Verify Vite workspace filesystem access and asset watch behavior. Use the same reload for a newly saved PNG. Preserve the last good draft in Studio on a failed write.
3. Add a small reconnect flow using the existing stored token/name (or a visible Retry button) after restart; distinguish ordinary restart from session fencing. A content revision/hash in server welcome/health and the client bundle can indicate mismatched versions while restart/reload is in flight; gate normal gameplay and retry/refresh when they differ. Compute the revision from the same canonical validated balance payload in both places. Production builds carry a content snapshot, so they must be rebuilt/redeployed with server balance changes; a mismatch is an explicit error, not silent conflicting HUD values.
4. Never reset SQLite as a reload side effect. Existing mobs keep current HP until death/respawn; increased max HP does not heal them and decreased max HP can leave current HP above the new max. Existing gear, XP and counters stay intact; new progression may change displayed level/maxima, inventory capacity or equipment behavior. Surface this in Studio and provide an optional **separate disposable test database** for fresh-world verification, not a reset button in v1. Changing starter data affects new characters only.

## 2. Art workflow: compare the options

| Approach | Best use and costs | Recommendation |
| --- | --- | --- |
| Paint pixels inside Studio | A tiny grid editor fits existing 16×16 icons and the exact `icons.json` format; pencil, eraser, palette, zoom, undo and a checkerboard deliver immediate control. Painting 48×48 terrain is possible later but tile seams, layers, selection and larger palettes turn this into an image editor. | Build icon painting first; preview the icon in the actual HUD scale. |
| Tune generators | `textures.ts`'s palettes and noise are scattered across distinct cases; a useful general parameter schema would be bespoke per generator and still yields repeated algorithmic texture. Current 3D character looks are solid boxes, not a noise generator. | Keep procedural generation as the fallback; expose no generic generator UI in v1. An occasional targeted palette adjustment is a code change. |
| Import Aseprite/PNG | External editors already support layers, palettes, precise tiling and art workflows. Import flattened PNG exports from Aseprite (no `.aseprite` parser or Aseprite executable dependency); validate dimensions/alpha and copy to an allowlisted local asset. | Build PNG import for one ground, wall, and roof asset next, expanding per material; this gives hand-drawn texture control without writing a paint suite. |

**Icons.** In Studio draw into the `pixels`/`palette` representation, not an opaque PNG blob. Optional PNG import can quantize or reject images whose palette exceeds 35 colors; never silently discard alpha or colors. Show which icons items/spells use. All imported icons must resolve to the same schema and export format.

**Terrain.** Add a manifest such as `content/textures.json` mapping `ground.grass`, `wall.timber`, and `roof.thatch` to explicit repository-relative PNG asset IDs under `content/textures/{ground,wall,roof}/`. Keep keys and allowed files fixed in v1. Sample shape: `{ "ground": { "grass": "ground/grass.png" }, "wall": { "timber": "wall/timber.png" }, "roof": { "thatch": "roof/thatch.png" } }`; an absent entry falls back to the current generator. Require 48×48 ground, 16×32 wall, 16×16 roof; keep color-space, nearest filters, no mipmaps, atlas layout, wrap modes, wall world-projection and roof UVs. Make a tiny repeat preview for seam inspection and a scene preview with adjacent tiles/walls/roof. Resolve assets through Vite static imports/explicit glob so the desktop build packages them; avoid arbitrary paths or runtime HTTP-only assets. Rebuild ground atlas/materials after loading images and pre-load before constructing the floor. For v1, leave animated water explicitly procedural and disable its import control; supporting authored water requires deliberately changing the shader to use the atlas color while retaining waves. Do not imply a PNG replaces it today. Similarly, distinguish `plankTexture()` prop wood from ground plank and leave props procedural initially.

**Characters and creatures.** The model JSON is colored cuboids on pivot groups. A lightweight part list with color, size, position and bone pivot controls, plus walk/idle/attack preview, makes existing rigs editable without flattening them. Preserve symmetric naming/ordering but do not force symmetry. A PNG cannot be imported as a character rig: hand-painted per-face box textures would require explicit UVs/materials and asset mapping; camera-facing sprites would require directional frames, animation, shadows and a renderer change. Defer both until the owner selects a visual direction. The model editor is complementary to the icon and texture pixel-art work, not a substitute for it.

### In-game appearance preview

Extract the existing reusable camera, sun/hemisphere settings, low-resolution render target and post shader from `apps/client/src/render/view.ts` into a shared renderer helper used by both `WorldView` and Studio. Reuse `buildFloor`/`worldMapped`, `groundAtlas`, and the actual `human`/`creature` builder for a small fixed sample scene, with the same orthographic camera angle, scaling, shadow settings, nearest sampling and ~215-pixel target. Offer surface sunset and cave/lamp presets using the actual `setFloor` logic, and a neutral raw-pixel view for authoring. HUD icons need a separate HUD preview because they do not go through the 3D post shader. Load draft art into the preview without saving; dispose replaced textures/materials/geometry only when owned and no longer shared. Make the first version use a full preview rebuild on save/change instead of complex resource swapping. Verify against the running game's same scene at the same resolution; a separately approximated light rig is not sufficient.

## 3. Balance tables and a real-engine simulator

### Editable tables and derived values

Expose items (weight, slot, attack/defense/armor, buy/sell, consumable values), creatures (HP, armor, attack, XP, gold range, loot chance, aggro and movement), spells (mana, level, cooldown and power), progression and merchant/quest/starter values. Units belong in headings (ms, HP, gold, weight); drafts are validated before Save. Keep stable IDs read-only. Show current and draft values alongside derived columns.

For a selected character preset (level or XP, raw skill counters, weapon/shield/armor, starting HP/mana/fed state), enemy and policy:

- **TTK and damage per kill:** report simulated mean/median and a range; include miss/zero-damage and deaths/timeouts. Report gross incoming hit damage and optionally net HP lost separately, since fed regen/healing can mask damage. Label metrics conditional on a kill if failures are excluded.
- **XP/hour and gold/hour:** show the assumptions alongside the numbers. A compact first estimate is `3600 × mean reward per successful kill / (mean successful fight seconds + assumed travel/loot seconds)`; label it a *sustained, successful-fight estimate*, not observed world throughput. Loot value is mean dropped gold plus `sum(chance × sell price)` only for items a merchant actually buys, under an explicit assumption that all drops are recovered and sold; show gross and subtract selected consumables for net. Do not imply it accounts for mortality, travel to shop, capacity, spawn competition or respawn constraints unless modeled. Example: a rat's expected gold plus sellable tails is `(0+4)/2 + 0.6×2 = 3.2` gold/kill; its loaf has no buyer in the current merchant lists.
- **Kills to afford:** `ceil((buy price − starting gold) / expected net gold per kill)` as a labeled planning ratio (clamp at zero); show unavailable if net ≤ 0 or no merchant sells the item. This is not the expected stopping time for random drops. Show the purchaser/seller assumptions.
- **Arbitrage:** warn when any merchant sells an item for `buy` and any merchant buys it for a strictly higher `sell` (including different merchants); zero buy price is relevant only if the item is actually sold. Also show the spread and involved roles. In `Engine.trade` these are global item prices with role-specific stock lists, and transport/time/capacity are not modeled.

Rates should not be presented as exact analytic outputs: `Engine.random(max)` draws integers inclusively with `floor(max)`, attack has random armor reduction and zero-damage hits, player and monster act at different times, attacks and skill increase occur before later events, XP can level a hero, food enables regeneration, and death resets HP and drops the pack. Surface the chosen assumptions rather than deriving TTK as HP divided by mean damage.

### Simulator design

Add `packages/game/src/simulation.ts` or a small studio worker importing the browser-safe `Engine`, `world.ts` and schemas; no Colyseus, SQLite or game server. Pass a validated **draft** `Balance` into the same `Engine` constructor used by the server. Build a deterministic, isolated small `MapData` with open tiles, a shrine, a single configured spawn and no other NPCs; use `emptyState`, `new Engine(...)`, `createPlayer`, equipment through the engine's item structures, `Engine.action(p, {kind:'target', id})`, and 100 ms `Engine.tick()` increments as in `tests/engine.test.ts` and the server. Set XP and raw skill counters directly in the fixture; if the UI accepts skill levels, invert the actual progression rules carefully rather than setting the counters equal to levels. Run repeated fights in a Web Worker so the UI stays responsive, each with a fresh state and reproducible nonzero `state.rng` seed; give scenarios fixed fixture IDs where identities affect ordering. Tick until the target dies, the hero dies, or an explicit time/iteration cap is reached.

Collect TTK, hit/regen/heal amounts, death, XP and corpse gold/loot from real engine events/state. The current `Effect` has positions, not actor IDs, and death immediately restores HP, so do not infer damage solely by final HP subtraction. Add a minimal optional observer/event record carrying actor ID, applied amount, and kill/death/loot information at existing mutation points, without changing combat order or RNG calls; alternatively use an equally faithful existing-state reconstruction. Disable unbounded notice/effect accumulation. For the initial policy use auto-melee and no consumables, with optional fed state; a subsequent policy can issue real `cast`/`useItem` actions at defined thresholds, obeying cooldown, mana and inventory, and record their costs. Clearly show preset, seeds, trial count, success/death/timeout percentages and simulated time. `Engine.dead` distributes XP differently for multiple players, but v1 is solo only. A follow-on continuous-farm mode may model availability, reset and downtime; do not extrapolate the isolated fight into a claim of actual in-world earnings.

The simulator stays in sync because it runs the exact `Engine.tick`, `think`, `cast`, `hurt`, `dead`, `stats`, and `random` code and the same parsed draft balance as the server, not a copied damage formula. Any extra observer records facts without making independent combat decisions. Add a deterministic comparison that runs the same preset and seed through the simulator and a direct Engine fixture and compares combat outcome, HP/XP, loot, time and RNG state; preserve the existing gameplay tests. Include a representative regression for spell spread and loot shape, and an invalid cross-reference test. These protect the boundary and parity rather than mirroring implementation.

## 4. Local app and safe file access

- Root `package.json`: `"studio": "vite --config apps/studio/vite.config.ts"`. Add `apps/studio/{package.json,index.html,vite.config.ts,src/main.ts,src/style.css}`; same TypeScript/Vite/Three stack, no Electron wrapper or server connection. Bind a separate strict port, e.g. `127.0.0.1:4174`; `npm run studio` works without `npm run dev`. Keep the frontend simple: Assets / Balance / Simulator, explicit Save, dirty-state indicator and validation errors.
- Add a Vite **dev-only** middleware in `apps/studio/vite.config.ts` or `apps/studio/server/content-api.ts`. `GET /api/content` returns the three validated files, manifest if present, and content hashes. `PUT /api/content/balance|icons|models|textures` accepts only the named complete document and an expected hash; PNG uploads use a similarly explicit asset ID mapping, not a path supplied by the client. Parse body as `unknown`, enforce reasonable size/content-type limits, validate the proposed document plus references against the other current files, and return field-level errors. Check current hash under a serialized write queue immediately before replacement; return `409` on an external edit, retaining the draft so the user can reload or reconcile. UI edits involving multiple files should be staged in a consistent order or rejected until references exist; per-file rename is atomic, a multi-file edit is not a transaction.
- Use server-side fixed paths resolved from `import.meta.url`, independent of cwd. Resolve/guard real paths against traversal and symlinks, accept only the fixed content/asset allowlist, and reject unknown names. Bind loopback, reject nonlocal Host and unexpected Origin, require same-origin requests and a custom JSON header/content type; avoid permissive CORS and use no arbitrary command/file endpoint. This protects the local write service from accidental web-page requests while keeping the workflow light.
- Validate the exact bytes to write and any image dimensions before creating a same-directory unique temporary file; write, flush/close, and rename over the destination, cleaning up on failure. Return success only after rename; retain original on validation/IO failure. For a PNG plus manifest, write the asset first and manifest last (or import to a new fixed asset ID); do not promise multi-file atomicity. Preserve existing content format with stable pretty-printed JSON and a trailing newline for reviewable diffs. The tool never touches `.local/lanternfall.sqlite`.
- Use only dev middleware for writes; no write endpoints in the built game. A studio restart or another editor changing a file must be visible via reload/hash conflict; the studio does not need collaboration, accounts or cloud sync.

## 5. Independently shippable milestones

1. **Validated data as the source of truth.** Add schemas and explicit balance injection, wire all existing exported balance fields to engine/client, icons to `icon()`, models to rig builder. Keep procedural terrain unchanged. Ship after `npm run typecheck`, `npm test`, `npm run build`, deterministic pre/post fixture parity, all 27 icon visual checks and all 12 rigs in idle/walk/attack. Verify game startup and a clean desktop build from bundled JSON. Baseline includes confirming exported values are actually equivalent; don't delete the old definitions before comparison.
2. **Small local editor + live game refresh.** `npm run studio`, middleware with validation, atomic writes and revision conflicts; direct 16×16 icon editing, palettes and undo. Add server watch/restart, client full reload/reconnect and revision mismatch handling. Acceptance: save an icon, see it in the game HUD; edit a creature stat, restart/reconnect, see it used on a fresh spawn; malformed input or an external conflict leaves the file intact. Demonstrate behavior using a disposable DB and separately confirm existing DB state is preserved.
3. **Balance workflow + solo fight simulator.** Editable, validated balance tables, per-item merchant arbitrage warnings, seeded worker-driven Engine fights and explicitly labeled TTK, damage, XP/hour, gold/hour and affordability estimates. Acceptance: unsaved draft changes affect simulation; after save the server uses the same snapshot; matching seeds give matching Engine outcomes, including a death and a spell scenario when spell policy is added. Start with auto-melee and extend to real action-based casts/consumables before claiming those policies are modeled.
4. **Hand-painted environment assets and shared visual preview.** Add explicit PNG manifest, 48×48 ground / 16×32 wall / 16×16 roof imports, fallback and repeat preview; integrate with actual terrain materials and shared game lighting/post. Acceptance: replace one of each in the studio, reload the game and packaged build, and see matching appearances. Water stays procedural until separately designed.
5. **Box-model editing.** Edit existing parts/bones/colors and preview human/creature idle, walk and attack using the actual rig builder. Acceptance: save/reload one human and one monster and verify pivots, shadow, height/label placement and no resource growth on repeated preview changes.

Each stage is useful on its own; the order puts writable validated data and icon work first, then the balance workflow, while keeping more involved renderer integration and model controls bounded. If the owner values ground art above numerical tuning, stages 3 and 4 can swap after stage 2.

## Explicitly leave out

- Accounts, multiplayer editing, cloud services, public hosting, deployment, external asset stores, or a production write API.
- A general Photoshop/Aseprite replacement: layers, animation timelines, selections, advanced brushes and `.aseprite` binary parsing.
- Automatic conversion of flat PNGs into voxel rigs, character sprite-sheet animation, generated art/AI, 3D model import, and a renderer overhaul.
- A general procedural-material parameter framework, editing water shader behavior, prop modeling, map editing, or automatically rebalancing the game.
- More IDs or content kinds without deliberate TypeScript/protocol/save migration; destructive world reset or live mutation of persisted players and monsters.
- Claims of exact economy predictions, multi-player farming, real-world drop/loot logistics, market dynamics, or perfect in-place HMR.

## Top five recommendations

1. Make the three existing content exports authoritative through shared Zod schemas and stable typed IDs; inject a validated balance snapshot into the real engine.
2. Use explicit save, validation, atomic writes and hash conflicts in a loopback-only Studio middleware; never modify the game database.
3. Ship a 16×16 icon painter and import flattened Aseprite PNG exports for hand-made ground/wall/roof art; keep generators as fallback.
4. Run reproducible solo simulations through `Engine.action` and `Engine.tick` with draft balance, and label rates, survival and economic assumptions.
5. Reuse the actual Three.js rig, light, camera and post-processing for previews; save-and-reload the game with clear restart, reconnection and persisted-state semantics.
