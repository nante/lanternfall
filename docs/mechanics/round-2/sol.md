## Blocking issues

1. **P1 — Attacks can originate inside a protection zone.** `packages/game/src/engine.ts:432`, `:459`, `:344`. The tick checks PZ status **before** applying movement, then executes melee without checking the new position. Offensive `cast()` never checks PZ at all. Reproduced with player `(22,26,0)`, target `(21,26,0)`, stand mode, then `walk(0,-1)`: the tick enters the shrine door `(22,25,0)` and deals 4 melee damage; casting Ember immediately afterward deals another 23 from inside PZ. This uses normal actions and the existing target, not a forged target assignment. **Exact fix:** after movement/travel, recheck the player's current PZ before the attack branch, cancel the attack target there, and add a PZ rejection inside the offensive branch of `cast()` before effects, damage, mana spending or training. Keep healing permitted. Add this boundary-crossing regression and a direct offensive-cast rejection test.

2. **P1 — Stand mode continues an existing chase route.** `packages/game/src/engine.ts:312`, `:434`, `:439`. Turning chase off only prevents generating another route; an existing automatic route still executes unconditionally. Reproduced: a three-step remaining chase path becomes two steps after `mode {chase:false}` and another eligible tick; the hero moves from `(51,45)` to `(52,45)`. **Exact fix:** on the transition to `chase:false`, clear `p.path` when `!p.manual`, preserving deliberate manual routes and the attack target. Verify that switching to stand stops further automatic steps while adjacent attacks continue.

3. **P1 — Diagonal animation exceeds its computed step duration.** `apps/client/src/render/view.ts:331`, `:435–436`. `stepMs` correctly includes the diagonal penalty, but rendering moves at `1000/stepMs × 1.05` world units/s. A diagonal covers √2 units, so it takes approximately `1.347 × stepMs`; a level-1 cobble diagonal configured for 1400 ms takes about 1886 ms. Successive diagonal steps can accumulate visible lag, and turns begin from unfinished positions. Cardinal steps also finish about 5% early. **Exact fix:** store each step's start position, start time and duration when the authoritative tile changes, then interpolate start→destination using elapsed/duration, clamped to 1. Interpolate the entire diagonal displacement over one duration; remove the `1.05` multiplier. Reset interpolation on teleports/floor changes. Verify consecutive diagonals and diagonal→cardinal turns.

4. **P1 — The scheduler silently rounds 50-ms movement back up to 100 ms.** `packages/game/src/engine.ts:417`, `:439`, `:447` (caller: `apps/server/src/index.ts:40`, `:62`). The formula returns 50-ms multiples, but production ticks only every 100 ms and schedules every following move from the late `now`. Reproduced at level 3 on shrine flagstone: each declared duration is 450 ms, but actual steps occur at 100, 600, 1100 and 1600 ms: 500-ms intervals. This loses the intended speed gain and disagrees with client animation/readiness. **Exact fix:** run simulation at 50-ms resolution and pass `50` explicitly to `engine.tick(50)` from the server interval (changing the interval alone would double game time because `tick()` defaults to 100). Alternatively process 50-ms simulation substeps within the existing caller. Add an engine test of successive actual move timestamps for a 450-ms tile, rather than testing only the stored deadline.

5. **P2 — Successful PZ logout leaves a ghost in the world.** `packages/game/src/engine.ts:310–311`, `:190`. The PZ exception accepts logout but retains `combatUntil`; `present()` therefore continues returning true. Reproduced in shrine with a future fight deadline: after logout, `connected:false`, `present:true`. The logged-out body keeps occupying tiles and ticking regeneration until the old deadline expires. **Exact fix:** on an accepted voluntary logout clear `combatUntil` along with the existing route/target cleanup, so `present()` immediately becomes false. Preserve fight retention for involuntary disconnects outside PZ. Verify successful PZ logout with an active fight deadline, and continue verifying rejection outside PZ.

## Non-blocking notes

1. `packages/game/src/rules.ts:32`, `:46`: magic requirements recursively multiply an already rounded previous threshold instead of calculating `ceil(1600 × 1.4^m)` independently. At ML4→5 the requirement is 6148 instead of 6147; at ML6→7 it is 12052 instead of 12048. Use one shared direct threshold function in `magic()` and `magicAt()` to match the stated formula and avoid accumulated rounding drift.
2. `tests/engine.test.ts:313–321`, `:356–363`: the shielding test allows four tries in a purported two-try window, lacks a positive training assertion, and does not force simultaneous eligible attacks. The PZ test never exercises monster targeting or entry despite its title. Replace these with controlled attack deadlines/positions: four attackers on one tick must consume exactly two opportunities, the next attacks before refill must consume none, and a PZ occupant must never become the monster target or admit a monster step. Shield training is defined by the consensus as using an opportunity with a shield, not necessarily fully absorbing the hit; update the title accordingly.
3. `packages/game/src/engine.ts:499–507`: actor Look returns before validating distance, floor or presence, while tile Look has a range check. An actor ID can reveal a remote/disconnected player's level or an off-floor monster's wound state; the existing Look test even looks at an underground rat from the surface. Resolve the actor, validate its actual position/presence with the same visibility/range policy, then describe it; do not trust the separately supplied `at` position as proof of reach.
